Warm-up: your temperature never arrived (5 min)

Your temperature=0 run gave 5 different results out of 10. In lesson 2, temperature 0 gave 1 out of 10. The reason is in how the arguments travel:

def extract(text, **options):        # extract(text, temperature=0)
    ...                              # options == {"temperature": 0}
    _ollama_call(role="user", content=text, options=options)

def _ollama_call(role, content, **options):
    ...                              # options == {"options": {"temperature": 0}}
    ollama.chat(..., options=options)

**options in a definition collects all keyword arguments into a dict. options=options in a call sends one keyword argument, named options. So the dict is wrapped one more time at each step. Ollama receives a key called "options", does not know it, and ignores it: all your runs were at the default temperature 0.8. (repeat has the same problem.) To unpack a dict into keyword arguments again, the call needs **options (Python tutorial: keyword arguments).

Task: fix the two calls, and make count use its parameter invoice_list (today it reads the global invoices_list). Then run your 10 repetitions again at temperature=0. How many different results now?

About your seed idea. "Find a seed that gives the right order number, and keep it." It feels logical, but it does not work, for two reasons. (1) At temperature 0 there is no random pick, so the seed does nothing. (2) At higher temperature, a seed that gives the right value on this invoice says nothing about the next invoice: the text is different, so the random numbers fall on different tokens. You would be tuning your system on one example. This is called overfitting. The only way to know if a change helps is to measure it on several documents. That is today's lesson.

The idea

An eval has three parts:

CasesFixed inputs. Today: 4 invoices in exercises/samples/.
Ground truthThe correct output for each case, checked by a human. Today: you.
ScoreA function that compares output and truth and gives a number. Today: correct fields out of total fields.

Hamel Husain, who builds LLM products for companies, puts it simply: "Unit tests for LLMs are assertions (like you would write in pytest)", and they "should run fast and cheaply as you develop your application" (Your AI Product Needs Evals). You already know this from testing your own code. The difference: the code under test is a model, and you never expect 100%. You expect a number, and you watch it move.

The second rule from the same article: "You can never stop looking at data". A score alone hides which fields fail. Your script will print every wrong field, with what the model gave and what you expected.

Step 1 · Write the ground truth (7 min)

There are three new invented invoices: invoice_002.txt, invoice_003.txt, invoice_004.txt. Read all four. Some are built to be hard: the supplier is not always at the top, and not every number near the word "ordine" is an order number.

Create exercises/samples/expected.json: one entry per file, with the 6 fields of your Invoice class. Rules, so the comparison is fair:

Step 2 · Write the eval (10 min)

In a new file eval.py, from this spec:

  • Import Invoice and extract from extract_data. Load expected.json.
  • A function same(got, want): for two strings, compare after .strip().casefold() (so S.R.L. equals S.r.l.); for a float, compare round(..., 2); otherwise == (this covers None).
  • For each file: extract(text, temperature=0), then invoice.model_dump() gives a dict. Compare each field. If extract returned None, all 6 fields are wrong.
  • Print each wrong field: file, field, got, want. At the end print the right answers per field and the total, like score 13/24.

Why only one run per file? At temperature 0 the output is repeatable (you just checked it in the warm-up), so one run is enough.

Try for 10 minutes before you open the solution.

Solution (open only after trying) 
import json
from pathlib import Path

from extract_data import Invoice, extract

SAMPLES = Path("samples")


def same(got, want):
    if isinstance(got, str) and isinstance(want, str):
        return got.strip().casefold() == want.strip().casefold()
    if isinstance(want, float):
        return got is not None and round(got, 2) == round(want, 2)
    return got == want


expected = json.loads((SAMPLES / "expected.json").read_text())
right = {field: 0 for field in Invoice.model_fields}

for name, want in expected.items():
    invoice = extract((SAMPLES / name).read_text(), temperature=0)
    got = invoice.model_dump() if invoice is not None else {}
    for field in right:
        if same(got.get(field), want[field]):
            right[field] += 1
        else:
            print(f"{name} {field}: got {got.get(field)!r}, want {want[field]!r}")

print(right)
print(f"score {sum(right.values())}/{len(expected) * len(right)}")

Note: extract must send an instruction before the text. Today your extract sends only the invoice (the instruction is in a comment). Put back "Extract the fields from this invoice.\n\n" + text.

Step 3 · Change one thing, measure again (8 min)

Look at the wrong fields. Probably supplier and customer are mixed up, and dates keep the document's format. Try two changes, one at a time, and run eval.py after each.

Change A: descriptions in the schema. Pydantic lets you attach a description to a field, and it goes into the JSON schema:

from pydantic import Field

    invoice_date: str = Field(description="Date of the invoice, format YYYY-MM-DD")
    supplier_name: str = Field(description="The company that issues the invoice and gets paid. Not the customer.")

Write descriptions for invoice_date, supplier_name, supplier_vat and order_number (say when it must be null). Predict the score, then run.

Change B: the schema in the prompt too. Keep the descriptions. Change the prompt to "Extract the fields from this invoice. Follow this JSON schema:\n" + json.dumps(Invoice.model_json_schema()) + the text. This is the tip from Ollama: structured outputs: "It is ideal to also pass the JSON schema as a string in the prompt to ground the model's response."

What this means for your agents

RuleWhy
Measure on several cases, never on oneA change that fixes one document can break another. Only the score on the whole set tells you.
The ground truth is written by a humanIf the model writes it, you measure the model against itself.
One change at a time, score after eachWith two changes at once you do not know which one helped.
Print the failures, not only the scoreThe failures tell you what to change next.

This set is tiny: 4 invoices. A real eval for the invoice pipeline of your mission needs dozens of verified documents. But the script does not change: you only add lines to expected.json. Every time you change the model, the prompt or the schema, you run it again.
