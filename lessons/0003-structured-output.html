Structured output: the format field

Lesson 3 · 30 minutes · Mission · Lesson 2 · Cheat sheet · Glossary

Today's win: you extract the fields of a sample invoice into a Python object with typed fields. Not text that looks like JSON: an object your code can use. You also see the main danger of this technique with your own eyes: a schema can force the model to invent a value.

Warm-up: one bug in repeat.py (3 min)

Your count_answers has this order of lines:

counts[response.message.content] += 1
if response.message.content is not None:
    clean_str: str = (response.message.content).strip()

The answer is counted before it is cleaned, and clean_str is never used. With cat names you had no problem, because the model added no spaces. Today the answers have many lines, and it will matter. Task: fix it so the cleaned string is the one that is counted.

The idea

A program cannot use a sentence. It needs fields: invoice.total, invoice.invoice_number. You can ask the model "answer in JSON", but that is only a request. The model may add a sentence before the JSON, or choose its own field names.

The format field is different. It is not a request, it is a limit. In lesson 2 you learned that the model picks one token at a time. With format, at each step Ollama removes the tokens that would break the schema, and the pick is made among the others. The output cannot have another shape. Ollama calls this structured output: "Structured outputs let you enforce a JSON schema on model responses so you can reliably extract structured data" (Ollama: structured outputs).

You do not write the JSON schema by hand. You write a Pydantic class (already installed: the ollama library uses it), and Pydantic gives you both directions:

from pydantic import BaseModel

class Invoice(BaseModel):
    invoice_number: str
    total: float

response = chat(model=..., messages=..., format=Invoice.model_json_schema())
invoice = Invoice.model_validate_json(response.message.content)
invoice.total        # a float, not a string
Invoice.model_json_schema()Class → schema. This is what you send to the model.
Invoice.model_validate_json(text)Text → object. It checks every field and type, and raises ValidationError if something is wrong.

Step 2 · Write the extractor (10 min)

In the same file, from this spec:

  • A class Invoice(BaseModel) with invoice_number: str, invoice_date: str, supplier_name: str, supplier_vat: str, total: float.
  • A function extract(text, **options) that returns an Invoice. The prompt is now short: Extract the fields from this invoice. plus the text. The field names are in the schema, so you do not repeat them.
  • It passes format=Invoice.model_json_schema() and options=options, and returns Invoice.model_validate_json(...).
  • The main part calls extract(text, temperature=0) and prints the object, then invoice.total * 2 to prove the total is a number.

Try for 10 minutes before you open the solution.

Solution (open only after trying) 
from ollama import chat
from pydantic import BaseModel

MODEL = "llama3.2:3b"


class Invoice(BaseModel):
    invoice_number: str
    invoice_date: str
    supplier_name: str
    supplier_vat: str
    total: float


def extract(text, **options):
    response = chat(
        model=MODEL,
        messages=[
            {"role": "user", "content": "Extract the fields from this invoice.\n\n" + text}
        ],
        format=Invoice.model_json_schema(),
        options=options,
    )
    return Invoice.model_validate_json(response.message.content)


with open("samples/invoice_001.txt") as f:
    text = f.read()

invoice = extract(text, temperature=0)
print(invoice)
print(invoice.total * 2)

What this means for your agents

RuleWhy
Every field that can be absent is ... | NoneA required field must be filled. If the document does not have the value, the model takes something that looks similar. The schema gives the model no way to say "not found" unless you add one.
format plus temperature: 0Ollama's own tip: "Lower the temperature (e.g., set it to 0) for more deterministic completions." Same document, same fields.
Always model_validate_json, never json.loads aloneYou get types checked, and one clear exception to catch when the output is cut or wrong.

One warning. The schema controls the shape, not the truth. "order_number": "conf. 100" is perfectly valid JSON, it passes validation, and it is false. Valid is not correct, in the same way that repeatable is not correct. Only a comparison with values you checked yourself can find this error. That comparison is an eval, and it is the next lesson.
